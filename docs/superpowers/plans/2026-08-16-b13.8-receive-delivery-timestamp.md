# B13.8 `ReceiveMessageResponse` 信封层 `delivery_timestamp` 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 sq 在有消息可投的 `ReceiveMessage` 响应里补发一帧信封层
`delivery_timestamp`，修复官方 Python SDK 的 PushConsumer 完全不可用。

**Architecture:** 单点改动。`internal/rpc/receive.go` 的 `ReceiveMessage` 在
「已确认本批有消息、进入发送循环之前」发一帧
`&pb.ReceiveMessageResponse{Content: &pb.ReceiveMessageResponse_DeliveryTimestamp{...}}`，
取值为该时刻的 `time.Now()`。空长轮询与全部错误分支保持原样不发。

**Tech Stack:** Go 1.24；生成的 pb 类型 `internal/rpc/pb/apache/rocketmq/v2`；
`google.golang.org/protobuf/types/known/timestamppb`；单测用 `internal/rpc` 包内
既有的进程内 gRPC 夹具（`newTestClient`）。

## Global Constraints

- spec：[`docs/superpowers/specs/2026-08-16-receive-delivery-timestamp-design.md`](../specs/2026-08-16-receive-delivery-timestamp-design.md)，
  D1–D4 是硬约束。
- 帧序固定为 `delivery_timestamp` → message × N → status。不得改动既有的
  status-last 帧序。
- 只在「本批有消息」时发；空长轮询（`MESSAGE_NOT_FOUND`）与所有错误分支
  （非 leader、非法过滤、topic 不存在、queueID 越界、deliver 错误）一帧都不加。
- 不改 proto、不改 `SystemProperties.DeliveryTimestamp` 的任何行为。
- 日志一律 `s.logger`（slog），禁止 `fmt.Printf`。
- 注释用中文，解释「为什么」。

- [ ] **Step 1: 写失败测试**

在 `internal/rpc/receive_test.go` 里把 `recvAll` 扩展为一并收集
`delivery_timestamp` 与「首帧类型」，再加两个用例。`recvAll` 现有调用点很多，
**不要改它的签名**——另写一个 `recvAllFrames` 返回完整帧序列，让新用例用它：

```go
// recvAllFrames 读整个 ReceiveMessage 流，原样保留帧序。
// 与 recvAll 的区别：它不做分类归约，用于断言帧的**位置**——
// 信封层 delivery_timestamp 必须是首帧（spec D2），归约后就看不出位置了。
func recvAllFrames(t *testing.T, stream pb.MessagingService_ReceiveMessageClient) []*pb.ReceiveMessageResponse {
	t.Helper()
	var frames []*pb.ReceiveMessageResponse
	for {
		resp, err := stream.Recv()
		if err == io.EOF {
			return frames
		}
		if err != nil {
			t.Fatalf("recv: %v", err)
		}
		frames = append(frames, resp)
	}
}

// TestReceiveSendsEnvelopeDeliveryTimestampAsFirstFrame 锁定 B13.8 的修复：
// 有消息可投时，响应流的首帧必须是信封层 delivery_timestamp。
//
// 为什么这条值得单独锁：缺这一帧时 Go/Java/C# 三门 SDK 全都若无其事
// （它们只是把值存进变量、容忍 nil），只有官方 Python SDK 会在 push 路径上
// 对它无条件做减法，抛异常 → 异常被吞 → listener 永不触发。也就是说，
// 这条帧的缺失在 Go e2e 里**照不出来**，只能靠这里的位置断言守住。
func TestReceiveSendsEnvelopeDeliveryTimestampAsFirstFrame(t *testing.T) {
	c := newTestClient(t)
	const topic = "envts"
	sendOne(t, c, topic, "hello")

	before := time.Now()
	// 只有落到消息所在队列的那次 receive 才会有消息；四个队列都试。
	var frames []*pb.ReceiveMessageResponse
	for q := int32(0); q < 4 && len(frames) < 2; q++ {
		ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
		stream, err := c.ReceiveMessage(ctx, &pb.ReceiveMessageRequest{
			Group:             &pb.Resource{Name: "g-envts"},
			MessageQueue:      &pb.MessageQueue{Topic: &pb.Resource{Name: topic}, Id: q},
			BatchSize:         8,
			InvisibleDuration: durationpb.New(time.Minute),
		})
		if err != nil {
			cancel()
			t.Fatalf("ReceiveMessage: %v", err)
		}
		frames = recvAllFrames(t, stream)
		cancel()
		if len(frames) < 2 {
			frames = nil // 这个队列没消息（只有一帧 MESSAGE_NOT_FOUND），换下一个
		}
	}
	after := time.Now()
	if len(frames) < 3 {
		t.Fatalf("期望至少 3 帧（delivery_timestamp + message + status），实际 %d", len(frames))
	}

	ts, ok := frames[0].GetContent().(*pb.ReceiveMessageResponse_DeliveryTimestamp)
	if !ok {
		t.Fatalf("首帧必须是信封层 delivery_timestamp，实际 %T", frames[0].GetContent())
	}
	got := ts.DeliveryTimestamp.AsTime()
	// 取值判据不能只判「非零」：非零可以由一个写死的常量满足。要求它落在
	// 本次调用的真实时间窗内，才能证明取的是「开始投递的那一刻」。
	if got.Before(before) || got.After(after) {
		t.Fatalf("delivery_timestamp %v 不在本次调用区间 [%v, %v] 内", got, before, after)
	}
	// 末帧仍是 status（sq 的 status-last 帧序不能被这次改动破坏）
	if _, ok := frames[len(frames)-1].GetContent().(*pb.ReceiveMessageResponse_Status); !ok {
		t.Fatalf("末帧必须是 status，实际 %T", frames[len(frames)-1].GetContent())
	}
	// 中间全是消息，且 delivery_timestamp 只发一帧
	for i, f := range frames[1 : len(frames)-1] {
		if _, ok := f.GetContent().(*pb.ReceiveMessageResponse_Message); !ok {
			t.Fatalf("第 %d 帧应为 message，实际 %T", i+1, f.GetContent())
		}
	}
}

// TestReceiveEmptyPollSendsNoDeliveryTimestamp 锁定 spec D1：空长轮询是
// sq 的常态热路径，不能因为这次改动被恒定加一帧。
//
// 这与参考实现刻意不同（上游在 finally 里无条件发），依据是没有任何已知
// SDK 在空响应下读它——判据与推翻它所需的证据都写在 spec D1。
func TestReceiveEmptyPollSendsNoDeliveryTimestamp(t *testing.T) {
	c := newTestClient(t)
	const topic = "envts-empty"
	sendOne(t, c, topic, "seed") // 只为建 topic；下面刻意读一个空队列
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()
	stream, err := c.ReceiveMessage(ctx, &pb.ReceiveMessageRequest{
		Group:             &pb.Resource{Name: "g-envts-empty"},
		MessageQueue:      &pb.MessageQueue{Topic: &pb.Resource{Name: topic}, Id: 3},
		BatchSize:         8,
		InvisibleDuration: durationpb.New(time.Minute),
	})
	if err != nil {
		t.Fatalf("ReceiveMessage: %v", err)
	}
	for _, f := range recvAllFrames(t, stream) {
		if _, ok := f.GetContent().(*pb.ReceiveMessageResponse_DeliveryTimestamp); ok {
			t.Fatal("空长轮询不应发信封层 delivery_timestamp（spec D1）")
		}
	}
}
```

> `envts-empty` 的队列 3 是否真的为空取决于发送轮询落点：`sendOne` 只发一条，
> 最多占住一个队列。若队列 3 恰好被占，把用例里的队列号换成一个未被占用的
> ——用 `recvAllFrames` 的帧数判断即可（只有一帧 status 即为空队列）。

- [ ] **Step 3: 实现**

在 `internal/rpc/receive.go` 的 `len(msgs) == 0` 分支之后、`for i, m := range msgs`
循环之前插入：

```go
	// 信封层 delivery_timestamp（proto 注释："The timestamp that brokers start
	// to deliver status line or message"）——该由 broker 发，sq 此前从不发。
	//
	// 为什么必须发：官方 Python SDK 的 push 路径对它做无保护减法
	// （client_metrics.py:151 `latency = current - transport_delivery_timestamp`），
	// 缺失即抛 TypeError；异常被 push_consumer.py 的 except 吞掉，同一 try 块里
	// 排在其后的 cache_messages / execute_consume 都不执行，listener 永不触发。
	// Go / Java / C# 只是把它存进变量、容忍 nil，所以这条缺口在 Go e2e 里
	// 全绿了很久（B13.8）。
	//
	// 为什么放批首而不像上游那样放批尾：sq 的 status 在末尾，是"本批已全部
	// 发完"的终止信号（见本函数上方"关于帧顺序"），metadata 帧挂在终止信号
	// 之后自相矛盾；批首也是 proto 注释 "start to deliver" 的字面语义。
	// 帧序对客户端无影响——Python 与 Go 都是收完整条流再按 oneof 分类。
	//
	// 为什么空批与错误分支不发（与上游刻意不同）：空长轮询是常态热路径，
	// 而没有任何已知 SDK 在空响应下读它。判据与推翻它所需的证据见
	// specs/2026-08-16-receive-delivery-timestamp-design.md 的 D1。
	deliveryTS := time.Now()
	if err := stream.Send(&pb.ReceiveMessageResponse{Content: &pb.ReceiveMessageResponse_DeliveryTimestamp{
		DeliveryTimestamp: timestamppb.New(deliveryTS),
	}}); err != nil {
		// 首帧就发不出去意味着流已经断了，后面的消息发了也没有意义。
		// 不能静默吞掉：吞掉就变成"客户端什么都没收到、服务端日志一片安静"。
		s.logger.Warn("ReceiveMessage 发送 delivery_timestamp 帧失败，流可能已被客户端关闭",
			"group", group, "topic", topic, "queue", queueID, "count", len(msgs), "err", err)
		return err
	}
```
