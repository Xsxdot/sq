# sq V2 复制层（三节点主备）设计

日期：2026-08-08
状态：已评审通过（brainstorm 定稿）
关联：[总设计](2026-08-06-sq-mq-design.md)（v2 版本节奏原句：「Raft 主备/集群（hashicorp/raft），3 节点，单机平滑升级」——本 spec 对选型与形态做了修订，见 §2）、[场景测试设计](2026-08-07-scenario-test-design.md)（已预留三节点集群实现位）

---

## 1. 目标与非目标

**目标**：sq 从单机升级为 3 节点复制集群——任一节点故障自动切换、不丢已确认消息、RocketMQ 官方客户端零改动兼容、三台机器都承担写流量（互为主备）。

**非目标**（明确划出去的）：

| 非目标 | 归属 | 理由 |
|---|---|---|
| 分片集群（横向扩展写吞吐） | V3 | 单机实测 57k msg/s（256 队列/256 并发，2 vCPU 云机），是 spec 目标 5k 的 11 倍；写扩展瓶颈不存在。本期用干净的「复制组」抽象预留：V3 分片 = 每分片一个复制组 + 一层路由，不返工 |
| follower 读 | 不做 | 收发都走 leader，一致性最简；MQ 的读本来就是写驱动的 |
| 真·多主（同队列双写） | 永不 | 队列 offset 连续有序，双写必碎；RocketMQ 亦不支持 |
| 外部仲裁（etcd/redis 选主） | 不做 | redis 类（redlock）无隔离令牌、依赖时钟假设，存储系统不可用；etcd 选主靠谱但要先运维一个 3 节点 etcd——比自身还重，违背单二进制定位。若将来有 k8s 场景可作 V3 适配器 |
| 2 数据节点 + 见证 | 不做 | 讨论过（见证 = 内嵌的只做选主的 etcd），最终定案统一 3 数据节点：形态唯一、测试矩阵最小、挂一台仍有双副本。两节点自动切换无第三票必脑裂，是物理约束不是实现选择 |
| 集群 → 单机降级 | 不支持 | 文档写明 |

## 2. 关键决策记录

### 2.1 选型：etcd/raft + 自建薄壳（修订原 spec 的 hashicorp/raft）

三方案对比结论：

| | dragonboat | **etcd/raft + 薄壳（选定）** | hashicorp/raft |
|---|---|---|---|
| 多组 | 原生，跨组 fsync 合并 | Cockroach/TiKV 生产验证过的模式，壳自己搭 | 单组设计，多组=多套实例，走不通 |
| 磁盘型 FSM | 专用接口 | 自主实现 | FSM 快照=全量序列化，为内存型状态机设计，模型不匹配 |
| 异步刷盘默认档 | 待验证，可能要 fork | **日志存储自主，策略完全自由** | 同样受限 |
| 共识内核风险 | 单人维护（lni），v4 长期 beta，出 bug 自己修 | 内核最稳（etcd/CockroachDB/TiKV 血脉），壳的 bug 归我们 | 内核稳但架构不匹配 |
| V3 百组分片 | 原生 | 模式正确，壳加调度 | 死路 |

选定理由：共识内核正确性风险必须压到最低；默认刷盘模式是非标需求（§5），自己管日志存储才不用跟库搏斗；sq 哲学是每一层自己看得懂。3 个固定组、固定成员、不分裂不迁移，薄壳规模约两三千行。dragonboat 为「快速见效」备选，若薄壳 spike 失败可回退。

### 2.2 刷盘模式：默认「复制确认 + 异步刷盘」

- 默认档：**quorum（2/3）节点内存确认**即向客户端返回——leader 写入本机内存并行发两 follower，任一 follower 确认即凑够 quorum，最慢节点不在关键路径。后台批量 fsync。对齐 Kafka / RocketMQ 异步刷盘默认。
  - 为什么内存确认有持久性：两台**独立故障域**机器的内存比一台机器的磁盘更难同时消失；配合 Raft 选举规则（日志最全者当选），任何单机故障（含 leader 整机断电）已确认消息不丢。唯一丢失窗口是多机在同一 flush 窗口（几百毫秒）内同时断电，即机房级事故（缓解：后台 flush 间隔可配）。
  - 明确排除「leader 内存确认即返回」：未达 quorum 的条目在选举后可被合法覆盖，任何单机故障都丢已确认消息，且违反 Raft 提交规则——这不是更快的档位，是复制保证归零（Redis 主从异步复制的 failover 丢数据即此模型）。
- 严格档（可配）：quorum 节点 fsync 后才返回。吞吐靠 raft 日志批量摊销，估计仍在万级。
- **安全性配套（必做，不可裸关 fsync）**：标准 Raft 假设投票/确认前日志已持久化；异步刷盘下节点崩溃重启会「失忆」。规则：**不干净重启的节点以 learner 身份重新加入，从 leader 快照/日志追齐后才恢复投票**。靠干净关机标记（clean-shutdown marker）检测。

### 2.3 吞吐结构变化（背景：08-08 三机实测）

单机时代吞吐定律：`吞吐 ≈ min(队列数, 并发)/2 × fsync 速率`（根源：每队列各自成批 fsync）。上 raft 后每组一条日志流，组内所有队列的写汇入，leader 按批追加——**一次 fsync 摊掉全部并发提案，合并度随并发涨、与队列数解耦**。粗估：批量 50 × 456 fsync/s × 3 数据组 ≈ 6.8 万 msg/s（同步刷盘档）；异步档更高。spike 实测标定（§8）。

## 3. 总体架构

```
  节点 A(sq)          节点 B(sq)          节点 C(sq)
  ┌──────────┐       ┌──────────┐       ┌──────────┐
  │ meta 组 L │◄─────►│ meta 组 F │◄─────►│ meta 组 F │   组0：元数据（全局）
  │ 数据组1 L │◄─────►│ 数据组1 F │◄─────►│ 数据组1 F │   ┐
  │ 数据组2 F │◄─────►│ 数据组2 L │◄─────►│ 数据组2 F │   ├ 队列按 hash 归组，
  │ 数据组3 F │◄─────►│ 数据组3 F │◄─────►│ 数据组3 L │   ┘ leader 摊布三机
  └──────────┘       └──────────┘       └──────────┘
        ▲                  ▲                  ▲
        └────────── RocketMQ 客户端 ──────────┘
          endpoints = "A:8081;B:8081;C:8081"
          QueryRoute 任意节点可答，队列地址指向其组 leader
```

- 3 个对等数据节点，每节点一个完整 sq 二进制（保持单二进制卖点）。
- 复制组默认 4 个：**1 元数据组**（topic 表、凭据、handle 签名密钥）+ **3 数据组**。组数可配，3 组配 3 节点是最小对称解。
- 队列 → 组映射：`hash(topic, queueID) % 数据组数`，稳定映射。
- 3 个数据组的 leader 通过 leadership transfer 摊到 3 台机器——互为主备的落地形态，每台吃约 1/3 写流量。
- handle 签名密钥入元数据组复制：failover 前签发的 receipt handle 在新 leader 上依然可验，消费不断链。

## 4. 写路径与复制

- **唯一拦截点**：B2 的类型化 batch（`store.NewBatch` 包一层类型使「唯一写入口」编译期成立）升级为 `replication` 隔离接口。两个后端：
  - 单机后端：batch 直接 `store.Apply`（今天的路径，零新开销）；
  - 集群后端：batch 字节作为 Command 提进所属 raft 组，quorum 确认后各节点 apply 到本地 Pebble。
- **复制物理 batch 字节而非逻辑命令**：只有 leader 构造 batch（offset 分配等逻辑只跑一次），follower 盲 apply，天然确定性；raft 库藏在接口后，将来换库是有限痛。
- **定时器类工作只在各组 leader 跑**：延迟消息投递、重投递扫描、retention。leader 变更时移交。
- 混 topic 批次经 hash 可能跨组——沿用 M7 的第一趟只读预检保证：预检通过后逐条按组提交，语义与单机一致（单条 at-least-once，无跨条原子性承诺）。

## 5. 存储布局与刷盘

- raft 日志与 FSM 数据**同一个 Pebble 实例**、不同 key 前缀，共享一条 WAL——刷盘策略全库一致，异步档下 quorum 内存确认即返回、后台批量 flush。
- `applied_index` 随 FSM 写原子持久化（同一 batch）；raft 日志保留至 FSM flush 过该 index 后方可截断（Pebble range delete）。
- 崩溃恢复：FSM 落后于 raft 日志 → 重放；日志有缺口（异步刷盘丢尾巴）→ 触发 §2.2 的 learner 追齐规则。

## 6. 客户端兼容与切换语义

- 客户端 endpoints 填 3 节点地址（官方 SDK 原生支持分号分隔多地址）。
- 任意节点应答 `QueryRoute`；每个队列的路由地址指向其组当前 leader。发到旧 leader → 可重试错误码，SDK 自动重试 + 刷路由。
- 切换窗口 = 选举时间（秒级）+ 客户端路由刷新周期（默认 30s，出错即刷可提前）。目标与实测值由 spike 标定。
- 语义保持 at-least-once：inflight 状态在组内复制，切换后 ack 照常生效；切换期间可能重复投递（协议本就允许）。

## 7. 单机模式与升级路径

- 单机模式**原样保留且仍是默认**：不跑 raft，零新开销，配置不写集群段即单机。
- 单机 → 集群平滑升级：现有数据目录作为第一个节点的初始状态启动集群模式，另两节点靠快照追齐入组。
- 集群 → 单机降级不支持。

## 8. 验证策略

1. **前置 spike**（进 plan 的第一批任务）：etcd/raft 薄壳搭最小三节点原型，实测——切换时间、同步/异步刷盘两档吞吐、learner 追齐耗时。数据回填本 spec §2.3。
2. **场景测试**：补上场景测试框架预留的集群节点实现，新增四类场景，不变量对账器原样复用：
   - kill leader（含 `kill -9`）；
   - 网络分区（少数派不可写、愈合后追齐）；
   - 滚动重启；
   - 断电模拟（`kill -9` + 丢未 flush 数据，校验「已确认消息不丢」——异步档允许丢未确认尾巴，已确认必须在）。
3. 单元层：薄壳的日志截断、快照追赶、干净关机标记均需独立测试；`-race` 全量在 Linux 跑（08-08 起 Linux 为一等验证平台）。

## 9. 依赖与排期约束

- **前置**：B2（类型化 batch）是本 spec §4 拦截点的地基，收编为 V2 第一个实现任务。
- **开工时机**：等性能优化会话 + M7 分支落地后基于稳定写路径开工（raft 拦截点就在写路径上，并行动码必然冲突且设计漂移）。
- backlog：V2 立 epic；「三节点以上分片集群」记为 V3 idea 行。
