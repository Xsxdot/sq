# 消费状态改 leader 内存权威态 + 周期检查点（SQ4.1）

> 状态：待批准（2026-11-11）
> 级别：**L2**（deliver 子系统内部改权威状态；消费 SQ1 新增的「可写 leader」判定，不另立跨子系统契约面——plan 若发现需改 Replicator/Router 接口签名，按跨流迁移升 L3 并回报）
> 卡：SQ4.1（父卡 SQ4）；并入并验收 SQ3；前置 SQ1、SQ2
> 用户裁决（2026-11-11）：检查点模式**默认开启**，可配置关回逐次复制

## 问题陈述

消费侧的状态（每个 消费组×topic×队列 的 fetch 位点 cursor，与该队列在外未确认消息的 inflight 记录）现在**以 pebble 为唯一权威**，每次取件、ack、改不可见、续租都「读 pebble → 组批次 → 复制 → 落盘」。由此三个问题（现状读数，基线 main@21ee680）：

1. **集群档重复投递、顺序锁失效（SQ3，已证实）**：`deliver.go:243-250` 在提案 apply 之前就放了队列锁，下一个持锁者从 pebble 读到旧 cursor / 旧 inflight。复现：集群档 2000 条里 136 个 offset 首投多次；顺序消息 60 轮里 55 轮同时在外超过一条。
2. **取件成本 O(inflight)**：`deliver.go:291-336` 每次取件、每次唤醒、每 100ms 兜底轮询都在队列锁内全量扫本队列 inflight 并逐条 JSON 解码。
3. **每条 ack 一次读盘 + 一次复制**：`deliver.go:625-669` 锁内 Get + JSON 解码；本机剖析（fsync=async 变体）里点查占 ack 路径 60% CPU，下层 65% 是 pread。Go SDK 的 PushConsumer 逐条 ack，集群档就是每条消息一个 raft 提案。

## 方案

**权威状态移到内存**：每个 (group, topic, queue) 的消费状态由**该队列所属 raft 组的可写 leader**（单机档即本进程）在内存持有：cursor、inflight 表（offset → 到期时间、投递次数、是否顺序、续租归属与预算）、在外顺序消息计数、按到期时间排序的索引。取件 / ack / 改不可见 / 续租 / 转死信 / 重置位点全部在队列锁内读写内存态，锁内即生效，不再读 pebble。

**持久化改为检查点**：内存态按队列周期性落盘为检查点——**每个队列的 cursor 与其全部 inflight 记录（增删改）写在同一个批次里**，经该队列所属组复制。

- 检查点模式（默认，`consume_checkpoint_interval: 1s`）：取件、ack 不等复制，锁内改完内存即返回。
- 逐次复制模式（`consume_checkpoint_interval: 0`）：每次取件/ack 的变更仍以「cursor + 变更的 inflight 同批」立即提案，并**在队列锁内**按调用顺序定序（依赖 SQ2 的保序提案队列），交件/应答前等提案完成——即现语义，只是读取改走内存，SQ3 一并根治。

**装载与失效**：
- 本节点成为某组的**可写 leader**（SQ1 引入的判定：applied 已追平本任期首条）后，首次访问某队列时从 pebble 的检查点装载内存态。
- 失去 leader 身份、或管理操作删除消费组数据（`adminops.go:127-148` 的 DeleteRange 旁路）时，丢弃对应内存态；下次装载重新读检查点。
- 未检查点的变更随失效丢弃——这就是「重复投递」的来源，见下。

**弃选**：
- 止血（集群档持队列锁到 Wait 返回）：用户 2026-11-11 否决，只修 SQ3 不解决 2、3。
- 只做内存态、持久化保持逐次复制并默认开启：用户选了检查点默认开启。
- 检查点只写 cursor、inflight 继续逐条写：cursor 可能领先于 inflight 落盘 → 丢消息，违反下面的不变式，否决。

## 安全语义（承重，验收以此为准）

**不变式 I1（不丢消息）**：任何时刻盘上（含任一副本）的 cursor 都不领先于它所覆盖区间的 inflight 记录——cursor 与 inflight 只在同一批次里一起写。由此崩溃 / 切主后从检查点恢复，凡是 cursor 之下、且没有 inflight 记录的 offset，都是在检查点时刻已被 ack 的。

**故障后果（检查点模式）**：只有**重复投递**，没有丢消息：
- 检查点之后被 ack 的消息会被重新投递（attempt 计数从检查点值继续）。
- 检查点之后投出的消息，其 inflight 不存在 → cursor 回退到检查点值 → 重新以新投递投出。
- 检查点之后的续租与改不可见丢失 → 可能提前重投。
- 量级 ≈ 检查点间隔 × 该队列消费速率（默认 1s）。顺序消息按顺序重放，不乱序。
- 进程正常停机（StopClean / SIGTERM 收尾）前做一次全量检查点，正常重启与主动转移 leader（TransferLeader）前同样先检查点，**计划内的切换不产生重复**。

**检查点与保留期**：retention 按消息存储时间删除，与消费进度无关（现状）；检查点回退区间内若有消息恰被 retention 删除，按「已过期」跳过，与慢消费者的现状一致，不算新增丢失。

## 必交故事

- **S1（SQ3 根治）**：集群档同一消费组多个消费者并发取同一队列，在 invisible 到期前，任一 offset 以 DeliveryAttempt=1 至多投出一次；顺序消息同一队列在外未确认的至多一条。验证：SQ3 复现用例（`worktree-agent-af9ad1270a441e9d9` 分支 `internal/core/deliver/sq3_cluster_race_test.go`，并入本卡分支）集群子测试转绿，连跑 ≥10 次稳定；单机子测试保持绿。两种模式（检查点 / 逐次复制）都要过。
- **S2（不丢消息，故障注入）**：持续生产 + 消费 + ack 的同时，(a) kill -9 leader 进程 (b) TransferLeader (c) 消费侧正常重启——每种之后，每条成功写入的消息都至少被投递一次；(b)(c) 下零重复。验证：本机三节点 e2e（`test/e2e` 集群场景），真机首跑项。
- **S3（重复有界）**：检查点模式下 kill -9 leader 后，重复投递条数 ≤ 检查点间隔内的投递量的合理倍数（plan 定精确判据）。同上环境。
- **S4（性能）**：取件成本与 inflight 数量无关；ack 不读盘。验证：deliver 包基准——现有 `BenchmarkAckParallel` 在 inflight 预置 1k / 10k 两档下 ns/op 不随 inflight 数增长；集群 e2e 写+消费吞吐对比基线（`TestClusterWriteThroughput` 同参数），报告实测数字。不设硬阈值，数字进卡。
- **S5（配置）**：`consume_checkpoint_interval` 缺省 1s；设 0 为逐次复制；负值或非法时长启动即拒并给出可读错误。验证：config 包测试。
- **S6（管理面一致）**：Admin「重置位点」「删除消费组」之后，下一次取件立刻按新状态投递（不被未失效的内存态覆盖）。验证：deliver/adminops 包测试 + e2e 已有管理面用例不回退。

## 实现决定

- 配置键 `consume_checkpoint_interval`（时长，缺省 `1s`，`0` = 逐次复制），写进 `sq.example.yaml` 与 `docs/configuration.md`，说明重复投递的取舍。
- 盘上格式**不变**：仍是现有 cursor 键与 inflight 键、inflight 值继续 JSON。只是写入时机变了。滚动升级期间新旧节点互读无障碍。
- inflight 改二进制编码**本卡不做**（理由：内存权威态后热路径不再编解码 inflight，JSON 只在检查点与装载时出现；改格式需两步升级），入 roadmap。
- 指标（`metrics/stats.go`）与控制台（`admin/groups.go`、`admin/timeseries.go`）继续读 pebble，看到的是检查点值，最多滞后一个检查点间隔；改走内存属 SQ4.9。
- 依赖 SQ1 的可写判定：未追平前对该组的消费请求按现有「非 leader」错误拒绝，客户端重试。

## 测试决定
